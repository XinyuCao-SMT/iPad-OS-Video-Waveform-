## 声画延时的基准：彩条与千周「起来的第一下」（用户决定）

**决定**：以**彩条出现的第一下**与**千周声起来的第一下**对齐作为判断标准。
`Sync-it` 素材与 ffmpeg 导帧那套**不再使用**，也不需要外部基准文件。

**怎么算**
- 视频事件 = 彩条出现的**第一帧**（亮度从基线抬起来的那一下）
- 音频事件 = 1 kHz 千周声的**起音**（第一次越过门限，且此前是安静的）
- 两者相减即延时；**这就是现有实现**（不需要"前后沿"两套事件）

**现有实现的位置（已与上述标准一致，无需改动）**
- 视频侧：`VideoScopePad.App\LiveSession.cs` → `DetectFlash`（彩条脉冲首帧）+ `PairSync`（就近配对 + 最近 5 次中位数）
- 音频侧：`VideoScopePad.Win\Audio\AvSyncAnalyser.cs`（包络 → 起音，样本级定位）
- 自检：`dotnet run --project tools\mf-capture -- avsync`（构造脉冲，逐轨分别测算，免硬件，5 项断言）

**现场用法**
1. 信号源给「彩条 + 千周」同时起来（一次即可，重复几次取中位数更稳）
2. 音频输入选与画面同源的（采集卡内嵌音频 / 同一信号源），避免声程差
3. 读「延时」——**直接看读数，不做任何补偿**（用户决定去掉固定补偿输入框，`SyncOffsetMs` 已删）。
   读数里如包含本程序 GPU 非阻塞回读造成的固有滞后，那也是真实可见的，不垫偏移掩盖

**已废弃**（保留说明，避免以后又绕回来）
- Sync-it 基准素材（`...Apple ProRes...mov`）与便携 ffmpeg 导帧/导音频流程
- `SyncTestMode.SyncIt` / `.Auto` 两个枚举值（已删，只剩 `BarsTone`）
- "彩条前后沿脉冲"的说法（用户澄清：只看起来的第一下，不分前后沿）
